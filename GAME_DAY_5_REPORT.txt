ARCHITECTURAL STRENGTHS
───────────────────────────────────────────────────────────────────────

1️⃣  PESSIMISTIC LOCKING (SELECT FOR UPDATE)
  The Settlement Engine acquires an exclusive row lock on the pick
  before any state transition (settlement_engine.py:71):

  ```python
  result = await db.execute(
      select(Pick).where(Pick.pick_id == pick_id).with_for_update()
  )
  ```

  This guarantees serialization of concurrent settlement attempts.

2️⃣  TERMINAL STATE VALIDATION (Lines 77-90)
  If the pick is already in a terminal state different from the target,
  a ConflictError is raised. This prevents:
    • won → void transitions
    • lost → won transitions
    • Any terminal state override

3️⃣  LEDGER-BASED CONFLICT DETECTION (Lines 92-104)
  Before executing a VOID, the engine checks if a PAYOUT or LOSS entry
  already exists in the ledger. This provides a cryptographic-grade
  audit trail for conflict resolution.

4️⃣  IDEMPOTENT SAME-STATUS TRANSITIONS (Lines 77-79)
  If pick.status == target_status, the engine returns immediately
  without modification. This makes retries safe and eliminates the
  need for application-level idempotency keys in many scenarios.

5️⃣  ATOMIC LEDGER + OUTBOX (Lines 128-147)
  Settlement writes to:
    • user_balances (via record_settlement)
    • ledger_entries (via record_settlement)
    • outbox_events (directly)
    • picks.status update

  All within the same transaction (db.begin_nested()). Either all
  commit or all rollback. No partial states possible.

OBSERVATIONS

🔍 HTTP 200 FOR IDEMPOTENT RESOLVE REQUESTS

  All 10 "won" requests returned HTTP 200 OK. This is correct behavior
  under the current idempotent success model. The engine detected that
  the pick was already in the target state and returned success without
  re-executing the settlement logic.

  TRADE-OFF:
    • PRO: Clients can safely retry without complex 409 handling
    • PRO: Network failures are transparent (retry = safe)
    • CON: Cannot distinguish "first success" from "nth success" in logs

  This is the same model validated in Game Day 4.0 and is considered
  optimal for BetSync's use case.
