OBSERVATIONS & RECOMMENDATIONS
───────────────────────────────────────────────────────────────────────

🔍 OBSERVATION:
  All 10 concurrent requests returned HTTP 200 OK, which suggests the
  settlement logic is idempotent rather than using optimistic locking
  with 409 Conflict responses.

📋 IDEMPOTENT SUCCESS MODEL (Current Implementation):
  PRO:
    • Simpler client retry logic (200 = success, always)
    • Better for unreliable networks (safe to retry)
    • Reduces false negatives for legitimate retries

  CON:
    • Cannot distinguish between "first success" and "repeated success"
    • May mask actual race conditions in monitoring
    • Harder to detect multi-click attacks

💡 ALTERNATIVE: OPTIMISTIC LOCK MODEL:
  Expected behavior:
    • 1st request: HTTP 200 OK + settlement executed
    • 2nd-10th: HTTP 409 Conflict + no-op

  PRO:
    • Clear distinction between first and repeated requests
    • Easier to monitor for race conditions
    • Explicit conflict signaling

  CON:
    • Clients must handle 409 as "successful idempotent retry"
    • More complex API contract
